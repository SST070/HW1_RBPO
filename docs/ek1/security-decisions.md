# Security Decisions

Проектные решения `D-*` связывают угрозы и требования с конкретным устройством минимальной технической основы. Для EK1 важно не количество механизмов, а объяснимость выбора и проверяемость цепочек.

## D-01 Token Gate And Owner-Scoped Store

Решение: все маршруты `/notes` проверяют заголовок `Authorization: Bearer <NOTES_API_TOKEN>`, а операции чтения, изменения и удаления проходят через методы `NotesStore`, которые принимают `ownerId`.

Где реализовано:

- `src/http.ts`: функция `requireBearerToken`;
- `src/http.ts`: все маршруты `/notes` вызывают `requireBearerToken` до работы с хранилищем;
- `src/store.ts`: методы `list`, `get`, `update`, `delete` фильтруют данные по `ownerId`.

Обоснование: для EK1 продукту нужна минимальная, но явная граница доверия. Bearer token проще полноценной учетной системы, но уже показывает обязательную авторизацию и единое место проверки доступа. Поле `ownerId` сохраняет путь к будущей многопользовательской версии.

### Alternatives

#### Alternative A: общий статический Bearer Token

Плюсы:

- очень просто реализовать;
- подходит для минимального учебного API;
- мало кода и зависимостей;
- легко показать на защите через `curl`.

Минусы:

- нет identity конкретного пользователя;
- сложно обеспечить полноценную owner isolation на HTTP-уровне;
- нет нормального expiry;
- неудобный revoke;
- плохо масштабируется на нескольких пользователей.

#### Alternative B: per-user JWT или server-side session

Плюсы:

- есть user identity;
- можно реализовать настоящую owner isolation;
- можно делать expiration;
- проще масштабировать на многопользовательский режим;
- можно добавить аудит действий по пользователю.

Минусы:

- сложнее реализация;
- появляются дополнительные security concerns;
- нужно управлять ключами или session store;
- увеличивается поверхность атаки.

Почему сейчас выбран A: для EK1 приложение является минимальным демонстрационным API, поэтому выбран статический Bearer Token. Решение нужно пересмотреть при появлении второго реального пользователя или требования разграничения доступа между пользователями.

Связи: `T-01`, `T-02`, `T-03`, `T-10` -> `SR-01`, `SR-02`, `SR-08`, `SR-09`.

Проверки:

- `D-01-V1`: отправить `GET /notes` без `Authorization`. Ожидаемый результат: `401`, тело ошибки не содержит stack trace.
- `D-01-V2`: отправить `GET /notes` с неверным Bearer Token. Ожидаемый результат: `401`.
- `D-01-V3`: отправить CRUD-запросы с корректным token. Ожидаемый результат: создание, чтение, обновление и удаление работают.
- `D-01-V4`: создать заметку с `ownerId = owner-a`, затем выполнить `GET`, `PATCH`, `DELETE` через `NotesStore` от имени `owner-b`. Ожидаемый результат: содержимое не раскрывается, изменение невозможно, удаление невозможно, возвращается `404`.

### Counterexample analysis

Исходное предположение: owner-scoped `NotesStore` гарантирует, что пользователь не сможет получить чужую заметку.

Контрпример: в HTTP-слое сейчас используется константа `OWNER_ID = "default-user"`. Если в системе появятся несколько реальных пользователей, все авторизованные HTTP-запросы будут иметь один `ownerId`. Получается, что корректный `NotesStore` сам по себе не обеспечивает изоляцию пользователей на HTTP-уровне.

Последствие: под угрозой оказываются `T-01`, `T-10`, `SR-02` и `D-01`.

Что требуется изменить: identity пользователя должна поступать из authenticated session, JWT или другого доверенного authentication context.

Новая проверка для будущей многопользовательской версии:

1. User A создает заметку.
2. User B делает `GET` этой заметки и получает `404`.
3. User B делает `PATCH` этой заметки и получает `404`.
4. User B делает `DELETE` этой заметки и получает `404`.
5. User A по-прежнему видит заметку.

## D-02 Strict Input Boundary

Решение: JSON-тело читается с лимитом 32 KiB, затем каждое поле заметки валидируется перед сохранением.

Где реализовано:

- `src/http.ts`: функция `readJson` считает прочитанные байты и ограничивает body;
- `src/store.ts`: `validateTitle`, `validateContent`, `validateTags`, `validateArchived`;
- `src/store.ts`: `create` и `update` вызывают валидаторы перед сохранением.

Обоснование: заметка является основным пользовательским объектом. Проверка типов, длины и количества тегов защищает минимальную основу от некорректных данных и простого расхода памяти.

Почему лимит 32 KiB: для личной заметки этого достаточно на EK1, при этом лимит мал и защищает простой in-memory сервис от очевидно чрезмерных запросов.

Связи: `T-04`, `T-05`, `T-11` -> `SR-03`, `SR-04`, `SR-09`.

Проверки:

- `D-02-V1`: отправить `POST /notes` с пустым `title`. Ожидаемый результат: `400`, код `validation_error`, заметка не создается.
- `D-02-V2`: отправить `POST /notes` с некорректным JSON. Ожидаемый результат: `400`, код `bad_json`, stack trace не раскрывается.
- `D-02-V3`: отправить JSON body больше 32 KiB. Ожидаемый результат: `400`, код `bad_json`, данные не сохраняются.
- `D-02-V4`: передать теги `["Work", "work", "EK1"]` в валидатор. Ожидаемый результат: `["work", "ek1"]`.
- `D-02-V5`: при будущей БД попытаться записать слишком длинные поля напрямую в persistence layer. Ожидаемый результат: ограничение схемы отклоняет запись.

## D-03 Uniform JSON Errors And Minimal Headers

Решение: ошибки API возвращаются единым JSON-форматом без stack trace, а ответы получают `X-Content-Type-Options: nosniff`.

Где реализовано:

- `src/http.ts`: `sendError`;
- `src/http.ts`: `sendJson`;
- `src/types.ts`: класс `ApiError` и перечисление кодов ошибок.

Обоснование: единый формат ошибок упрощает клиентскую обработку и снижает риск случайного раскрытия внутренних деталей. Заголовок `nosniff` задает базовую защиту для JSON API без усложнения архитектуры.

Почему не делали сложную систему логирования: к EK1 важнее безопасный внешний ответ. Логи и корреляционные id полезны, но относятся к следующему этапу наблюдаемости.

Связи: `T-03`, `T-06`, `T-07` -> `SR-05`, `SR-06`.

Проверки:

- `D-03-V1`: отправить некорректный JSON. Ожидаемый результат: единый JSON-ответ `{ "error": ... }`.
- `D-03-V2`: проверить любой JSON-ответ API. Ожидаемый результат: есть `X-Content-Type-Options: nosniff`.
- `D-03-V3`: искусственно вызвать unexpected error в тестовой сборке. Ожидаемый результат: клиент получает `internal_error`, без stack trace и секретов.
- `D-03-V4`: при добавлении CORS отправить запрос с разрешенным и запрещенным `Origin`. Ожидаемый результат: CORS headers соответствуют политике.

## D-04 Persistence-Ready Ownership Model

Решение: даже в in-memory версии объект заметки уже содержит `ownerId`, а все операции хранилища принимают владельца как обязательный аргумент.

Где реализовано:

- `src/types.ts`: тип `Note` содержит `ownerId`;
- `src/store.ts`: методы `list`, `get`, `update`, `delete` требуют `ownerId`.

Обоснование: это не полноценная многопользовательская система, но это важное проектное решение. Оно предотвращает ситуацию, когда будущую авторизацию приходится добавлять поверх модели, где заметки никак не связаны с владельцем.

Связи: `T-01`, `T-03`, `T-10`, `T-11` -> `SR-02`, `SR-08`, `SR-09`.

Проверки:

- `D-04-V1`: создать заметку от `owner-a`, затем прочитать ее от `owner-b`. Ожидаемый результат: `404`.
- `D-04-V2`: создать заметку от `owner-a`, затем обновить ее от `owner-b`. Ожидаемый результат: `404`, исходная заметка не изменилась.
- `D-04-V3`: создать заметку от `owner-a`, затем удалить ее от `owner-b`. Ожидаемый результат: `404`, `owner-a` по-прежнему видит заметку.
- `D-04-V4`: при добавлении БД проверить, что `UPDATE` и `DELETE` выполняются с условием по `owner_id`.

## D-05 Configuration Hygiene

Решение: секреты и локальные настройки не хранятся в Git; token передается через переменную окружения `NOTES_API_TOKEN`; `.env` исключен через `.gitignore`.

Где реализовано:

- `.gitignore`: исключает `.env`, `dist`, `.test-dist`, `node_modules`;
- `src/main.ts`: читает `NOTES_API_TOKEN` из окружения и не запускает сервис без него;
- `README.md`: показывает только демонстрационный `dev-token`, а не реальный секрет.

Обоснование: текущая авторизация полностью зависит от секрета. Если секрет попадает в репозиторий, bearer-token gate перестает защищать API.

Связи: `T-09` -> `SR-07`.

Проверки:

- `D-05-V1`: выполнить `git ls-files` и убедиться, что `.env` и `.env.*` не отслеживаются.
- `D-05-V2`: выполнить поиск по tracked-файлам на реальные значения `NOTES_API_TOKEN`. Ожидаемый результат: реальные секреты отсутствуют.
- `D-05-V3`: запустить сервис без `NOTES_API_TOKEN`. Ожидаемый результат: процесс завершается с ошибкой конфигурации.

## Основная цепочка для защиты

```text
T-01 Unauthorized Disclosure
  -> SR-01 Authentication Required + SR-02 Note Ownership Isolation
  -> D-01 Token Gate And Owner-Scoped Store
  -> D-01-V1 / D-01-V4
```

Почему решение подходит: оно закрывает наиболее прямой риск сервиса заметок - доступ к личному содержимому без права. Даже в минимальной версии API все операции с заметками проходят через одну проверку bearer token, а доступ к объектам идет через owner-scoped методы хранилища.

Короткая формулировка для устной защиты: “Мы считаем HTTP-запрос недоверенным. До работы с заметками проверяем bearer token, а сами заметки достаем не просто по id, а по паре ownerId + id. Поэтому прямой обход через чужой id не должен раскрывать объект”.
