# Security Requirements

Требования сформулированы для минимальной версии Notes Service на EK1. Каждое требование имеет устойчивый идентификатор `SR-*`, критерии приемки и связь с угрозами `T-*`.

## SR-01 Authentication Required

Все операции с заметками должны выполняться только при наличии корректного bearer token.

Мотивация: заметки являются личными данными пользователя. Даже в минимальной версии нельзя оставлять CRUD-маршруты открытыми.

Критерии приемки:

- `GET /health` доступен без token, потому что это техническая проверка живости;
- `GET /notes`, `POST /notes`, `GET /notes/:id`, `PATCH /notes/:id`, `DELETE /notes/:id` без заголовка `Authorization` возвращают `401`;
- те же маршруты с неверным token возвращают `401`;
- сервис не запускается без переменной окружения `NOTES_API_TOKEN`;
- значение token не хранится в исходном коде и не коммитится в репозиторий.

Связанные угрозы: `T-01`, `T-02`, `T-09`.

Текущий статус: частично реализовано и проверяется тестами для отказа без token; неверный token обрабатывается тем же механизмом.

## SR-02 Note Ownership Isolation

Пользователь не должен получать доступ к заметкам другого владельца.

Мотивация: при появлении нескольких пользователей основным риском станет горизонтальное нарушение доступа, когда один пользователь обращается к объекту другого.

Критерии приемки:

- каждая заметка имеет `ownerId`;
- список заметок фильтруется по `ownerId`;
- чтение, обновление и удаление проходят через owner-scoped методы хранилища;
- чужая заметка возвращает `404`, а не `403`, чтобы не подтверждать факт существования объекта;
- тест хранилища показывает, что `owner-b` не может прочитать заметку `owner-a`.

Связанные угрозы: `T-01`, `T-03`, `T-10`.

Текущий статус: реализовано на уровне `NotesStore`; HTTP-слой пока использует одного владельца `default-user`.

## SR-03 Input Validation

Сервис должен проверять недоверенные поля заметки перед сохранением.

Мотивация: заметка приходит из внешнего HTTP-запроса. Без валидации можно сохранить пустые, чрезмерно длинные или структурно некорректные данные.

Критерии приемки:

- `title` обязателен;
- `title` после `trim` имеет длину 1-120 символов;
- `content` является строкой и имеет длину не более 10000 символов;
- `tags` является массивом строк;
- количество тегов не больше 12;
- каждый тег после `trim` имеет длину 1-32 символа;
- теги нормализуются к нижнему регистру;
- дубликаты тегов удаляются;
- некорректные данные возвращают `400` и код `validation_error`.

Связанные угрозы: `T-04`, `T-05`, `T-11`.

Текущий статус: реализовано в `src/store.ts`, частично подтверждено тестами.

## SR-04 Request Body Limit

Сервис должен ограничивать размер JSON-тела запроса.

Мотивация: даже простой API может быть перегружен большим телом запроса. Поскольку EK1-версия хранит данные в памяти, ограничение размера тела особенно важно.

Критерии приемки:

- JSON-тело больше 32 KiB отклоняется;
- некорректный JSON отклоняется;
- ошибка имеет единый формат JSON;
- сервис не должен пытаться сохранить частично прочитанные данные.

Связанные угрозы: `T-05`, `T-11`.

Текущий статус: реализовано в `readJson` с лимитом `JSON_LIMIT_BYTES`.

## SR-05 Safe Error Responses

Ответы об ошибках не должны раскрывать stack trace, переменные окружения или внутреннее устройство процесса.

Мотивация: подробная диагностика полезна разработчику, но опасна во внешнем API. Она помогает атакующему понять структуру сервиса.

Критерии приемки:

- известные ошибки возвращаются в формате `{ "error": { "code": "...", "message": "..." } }`;
- неожиданные ошибки возвращают общий код `internal_error`;
- в ответе нет stack trace;
- в ответе нет значения `NOTES_API_TOKEN`;
- сообщение не раскрывает, принадлежит ли объект другому пользователю.

Связанные угрозы: `T-03`, `T-06`.

Текущий статус: реализовано для ошибок `ApiError` и fallback `internal_error`.

## SR-06 Minimal Security Headers

JSON-ответы должны снижать риск неверной интерпретации содержимого клиентом.

Мотивация: API возвращает JSON. Клиенты и промежуточные компоненты не должны пытаться интерпретировать его как HTML или другой тип.

Критерии приемки:

- каждый ответ сервиса содержит `X-Content-Type-Options: nosniff`;
- JSON-ответы содержат `Content-Type: application/json; charset=utf-8`;
- тест подтверждает наличие `nosniff` хотя бы на одном маршруте API.

Связанные угрозы: `T-07`.

Текущий статус: реализовано в `sendJson`.

## SR-07 Version Observability

Оцениваемая версия должна быть зафиксирована в Git и проверяема локально.

Мотивация: для EK1 важно не только иметь код, но и однозначно показать, какая версия сдается и как она воспроизводится.

Критерии приемки:

- в репозитории есть исходный код запускаемого API;
- в `README.md` и `PROJECT.md` есть команды запуска;
- в `PROJECT.md` описан ожидаемый наблюдаемый результат;
- есть commit hash оцениваемой версии или tag `ek1`;
- `CONTRIBUTIONS.md` связывает вклад участников с конкретными результатами;
- `AI_USAGE.md` явно описывает использование ИИ.

Связанные угрозы: `T-08`.

Текущий статус: реализовано; версия фиксируется Git-коммитом и может быть дополнительно отмечена tag `ek1`.

## SR-08 Configuration Hygiene

Секреты и локальные настройки не должны попадать в репозиторий.

Мотивация: token авторизации в минимальной версии является секретом. Если его закоммитить, весь механизм авторизации теряет смысл.

Критерии приемки:

- `.env` и `.env.*` исключены через `.gitignore`;
- пример запуска использует демонстрационный `dev-token`, а не реальный секрет;
- `NOTES_API_TOKEN` читается только из окружения;
- документация явно говорит, что production token должен задаваться вне Git.

Связанные угрозы: `T-09`.

Текущий статус: реализовано через `.gitignore` и `src/main.ts`.

## SR-09 Safe Deletion Semantics

Удаление заметки должно быть явным и ограниченным владельцем.

Мотивация: удаление нарушает доступность и целостность данных. Даже если в EK1 нет постоянной БД, поведение API должно быть определено заранее.

Критерии приемки:

- `DELETE /notes/:id` требует token;
- удаление вызывает owner-scoped проверку;
- после удаления повторное чтение возвращает `404`;
- удаление не возвращает тело с внутренними деталями объекта.

Связанные угрозы: `T-01`, `T-10`.

Текущий статус: реализовано и проверяется тестом.

## SR-10 Future Persistence Controls

При переходе от in-memory хранилища к БД требования авторизации и валидации должны сохраниться на уровне схемы и запросов.

Мотивация: EK1-версия не использует БД, но проект должен показать, как текущие решения масштабируются дальше.

Критерии приемки для будущей версии:

- таблица заметок содержит `owner_id`;
- запросы к БД фильтруют данные по `owner_id`;
- ограничения длины полей дублируются в схеме или миграциях;
- удаление и обновление выполняются с условием по `owner_id`;
- тесты покрывают невозможность доступа к чужим объектам.

Связанные угрозы: `T-01`, `T-03`, `T-10`.

Текущий статус: запланировано как развитие после EK1.
