# Threat Model

Модель угроз описывает минимальную версию Notes Service на EK1. Методика простая: сначала фиксируем активы и границы доверия, затем перечисляем угрозы, оцениваем вероятность и ущерб, выбираем приоритетный набор для защиты.

## 1. Контекст

Продукт: HTTP API личных заметок.

Основной защищаемый объект: заметка пользователя, включая `title`, `content`, `tags`, `createdAt`, `updatedAt`, `archived`.

Текущая архитектура:

- один Node.js процесс;
- HTTP API на стандартном модуле `node:http`;
- bearer token из `NOTES_API_TOKEN`;
- in-memory хранилище `Map<string, Note>`;
- один текущий владелец `default-user` на уровне HTTP;
- owner-scoped методы в доменной логике.

## 2. Участники и роли

| Роль | Возможности | Доверие |
| --- | --- | --- |
| Обычный пользователь | Отправляет HTTP-запросы к API | Недоверенный до проверки token |
| Авторизованный пользователь | Знает корректный bearer token | Доверен только в рамках своих заметок |
| Злоумышленник без token | Может отправлять запросы на публичные маршруты | Недоверенный |
| Разработчик/оператор | Запускает сервис и задает `NOTES_API_TOKEN` | Доверенный для EK1 |
| Преподаватель на защите | Проверяет запуск, код и документы | Не участник угроз, но важен для наблюдаемости |

## 3. Приоритетная шкала

Оценка приоритета учитывает два фактора:

- вероятность: насколько легко выполнить действие в текущей архитектуре;
- ущерб: насколько сильно нарушается конфиденциальность, целостность или доступность.

Высокий приоритет означает, что угроза относится к основной границе доверия или может обнулить ценность продукта. Средний приоритет означает значимый риск, который важно учесть в проектном решении. Низкий приоритет означает полезное hardening-требование или будущий риск.

## 4. Угрозы

## T-01 Unauthorized Note Access

Злоумышленник пытается прочитать, изменить или удалить заметки без права доступа.

Приоритет: высокий.

Вероятность: высокая, если CRUD-маршруты доступны без общей проверки.

Ущерб: высокий, потому что нарушается конфиденциальность и целостность личных заметок.

Обоснование: заметки могут содержать личную, учебную или рабочую информацию. CRUD API является основной поверхностью продукта.

Связанные требования: `SR-01`, `SR-02`, `SR-09`, `SR-10`.

Связанные решения: `D-01`, `D-04`.

## T-02 Token Guessing Or Omission

Клиент отправляет запрос без token, с пустым token или со случайным значением.

Приоритет: высокий.

Вероятность: высокая, потому что такой запрос легко отправить вручную.

Ущерб: высокий, если сервис ошибочно принимает такой запрос.

Обоснование: это базовая проверка границы доверия. Если она отсутствует или применяется не ко всем маршрутам, остальные решения теряют смысл.

Связанные требования: `SR-01`.

Связанные решения: `D-01`.

## T-03 Object Enumeration

Злоумышленник перебирает `id` заметок и пытается определить, какие записи существуют.

Приоритет: средний.

Вероятность: низкая для UUID, но не нулевая как класс атаки.

Ущерб: средний, потому что даже факт существования заметки может быть метаданными.

Обоснование: UUID затрудняет перебор, но API не должен помогать различать чужую заметку и несуществующую.

Связанные требования: `SR-02`, `SR-05`, `SR-10`.

Связанные решения: `D-01`, `D-03`, `D-04`.

## T-04 Invalid Note Data

Клиент отправляет пустые заголовки, слишком длинный текст, некорректные теги или поля неверного типа.

Приоритет: средний.

Вероятность: высокая, потому что любой HTTP-клиент может отправить произвольный JSON.

Ущерб: средний, потому что портится качество данных и усложняется дальнейшая работа клиента.

Обоснование: без валидации данные быстро ломают пользовательские сценарии, UI и будущую БД.

Связанные требования: `SR-03`.

Связанные решения: `D-02`.

## T-05 Oversized JSON Body

Клиент отправляет слишком большой JSON и расходует память процесса.

Приоритет: высокий.

Вероятность: средняя, потому что атаку легко выполнить, но лимит тела прост в реализации.

Ущерб: высокий для минимального Node.js процесса, особенно если запросов много.

Обоснование: сервис хранит данные в памяти и читает body из потока, поэтому нужен явный лимит.

Связанные требования: `SR-03`, `SR-04`.

Связанные решения: `D-02`.

## T-06 Diagnostic Data Exposure

Неожиданная ошибка раскрывает stack trace, переменные окружения или внутренние детали сервиса.

Приоритет: средний.

Вероятность: средняя, потому что ошибки появляются при развитии проекта.

Ущерб: средний, потому что диагностические данные помогают строить дальнейшие атаки.

Обоснование: API должен возвращать клиенту только безопасное описание ошибки.

Связанные требования: `SR-05`.

Связанные решения: `D-03`.

## T-07 Content Sniffing

Клиент или промежуточный компонент неверно интерпретирует JSON-ответ как другой тип содержимого.

Приоритет: низкий.

Вероятность: низкая для текущего API.

Ущерб: низкий в backend-only версии, но решение дешевое.

Обоснование: `X-Content-Type-Options: nosniff` является простым hardening-механизмом.

Связанные требования: `SR-06`.

Связанные решения: `D-03`.

## T-08 Unverifiable EK1 Version

Команда не может однозначно показать, какой код и документы оцениваются.

Приоритет: высокий.

Вероятность: средняя, если нет отдельного репозитория, tag или commit hash.

Ущерб: высокий для EK1, потому что преподаватель не может проверить состав сдачи и вклад.

Обоснование: наблюдаемость результата является отдельным критерием EK1.

Связанные требования: `SR-07`.

Связанные решения: `D-05`.

## T-09 Token Leakage Through Repository

Секретный token попадает в Git, README, лог или пример конфигурации.

Приоритет: высокий.

Вероятность: средняя, потому что при разработке удобно копировать `.env` и реальные значения.

Ущерб: высокий, потому что token открывает доступ к операциям с заметками.

Обоснование: текущий механизм авторизации полностью зависит от секрета `NOTES_API_TOKEN`.

Связанные требования: `SR-01`, `SR-08`.

Связанные решения: `D-05`.

## T-10 Unauthorized Modification Or Deletion

Злоумышленник не только читает, но и изменяет или удаляет чужую заметку.

Приоритет: высокий.

Вероятность: средняя, если доступ к объектам проверяется только при чтении.

Ущерб: высокий, потому что нарушается целостность и доступность данных.

Обоснование: изменение и удаление должны проходить через те же owner-scoped проверки, что и чтение.

Связанные требования: `SR-02`, `SR-09`, `SR-10`.

Связанные решения: `D-01`, `D-04`.

## T-11 Validation Bypass During Future Persistence

При переходе к БД часть ограничений остается только в коде HTTP-слоя и обходится другим путем записи.

Приоритет: средний.

Вероятность: средняя на будущих этапах проекта.

Ущерб: средний, потому что в БД могут появиться некорректные или чрезмерные данные.

Обоснование: EK1 должен показать направление развития, поэтому будущие ограничения БД фиксируются заранее.

Связанные требования: `SR-03`, `SR-04`, `SR-10`.

Связанные решения: `D-02`, `D-04`.

## 5. Приоритетный набор EK1

Для подробной защиты выбраны:

- `T-01 Unauthorized Note Access`;
- `T-02 Token Guessing Or Omission`;
- `T-05 Oversized JSON Body`;
- `T-08 Unverifiable EK1 Version`;
- `T-09 Token Leakage Through Repository`;
- `T-10 Unauthorized Modification Or Deletion`.

Почему именно они:

- `T-01`, `T-02`, `T-10` покрывают главную границу доверия: кто может обращаться к заметкам и что он может делать;
- `T-05` покрывает устойчивость минимального HTTP API к недоверенному телу запроса;
- `T-08` нужен для самого формата EK1 и наблюдаемости результата;
- `T-09` связан с выбранным механизмом token-авторизации.

## 6. Угрозы вне рамок EK1

Эти угрозы признаются, но не закрываются полностью к EK1:

- подбор слабого production token;
- rate limiting и brute force;
- HTTPS termination;
- полноценное управление пользователями;
- хранение заметок в постоянной БД;
- аудит действий;
- шифрование содержимого заметок;
- восстановление удаленных заметок.

Они вынесены в будущие проверки и развитие решений, потому что EK1 требует минимальную запускаемую основу и концепцию безопасности, а не завершенный production-релиз.
