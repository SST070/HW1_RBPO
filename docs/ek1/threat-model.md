# Threat Model

## T-01 Unauthorized Note Access

Злоумышленник пытается прочитать, изменить или удалить чужие заметки без права доступа.

Приоритет: высокий.

Обоснование: заметки могут содержать личную или учебную информацию, а CRUD API является основной поверхностью продукта.

Связанные требования: `SR-01`, `SR-02`.

## T-02 Token Guessing Or Omission

Клиент отправляет запрос без токена, с пустым токеном или со случайным значением.

Приоритет: высокий.

Обоснование: это самый простой путь к обходу границы доверия, если проверка авторизации отсутствует или применяется не ко всем маршрутам.

Связанные требования: `SR-01`.

## T-03 Object Enumeration

Злоумышленник перебирает `id` заметок и пытается определить, какие записи существуют.

Приоритет: средний.

Обоснование: UUID снижает вероятность успешного перебора, но ответы API не должны помогать отличать чужую заметку от несуществующей.

Связанные требования: `SR-02`.

## T-04 Invalid Note Data

Клиент отправляет пустые заголовки, слишком длинный текст, некорректные теги или поля неверного типа.

Приоритет: средний.

Обоснование: без валидации данные быстро ломают пользовательские сценарии и усложняют дальнейшую реализацию UI и хранения.

Связанные требования: `SR-03`.

## T-05 Oversized JSON Body

Клиент отправляет слишком большой JSON и расходует память процесса.

Приоритет: средний.

Обоснование: сервис минимальный и хранит данные в памяти, поэтому простое ограничение размера тела важно уже на EK1.

Связанные требования: `SR-03`, `SR-04`.

## T-06 Diagnostic Data Exposure

Неожиданная ошибка раскрывает stack trace, переменные окружения или внутренние детали сервиса.

Приоритет: средний.

Обоснование: диагностическая информация помогает строить дальнейшие атаки и ухудшает безопасность публичного API.

Связанные требования: `SR-05`.

## T-07 Content Sniffing

Клиент или промежуточный компонент неверно интерпретирует JSON-ответ как другой тип содержимого.

Приоритет: низкий.

Обоснование: риск ниже, чем у авторизации и валидации, но заголовок `nosniff` дешевый и полезный.

Связанные требования: `SR-06`.

## T-08 Unverifiable EK1 Version

Команда не может однозначно показать, какой код и документы оцениваются.

Приоритет: высокий.

Обоснование: без commit hash или tag `ek1` невозможно надежно подтвердить состав сдаваемого комплекта и вклад.

Связанные требования: `SR-07`.

## Приоритетный набор

Для EK1 приоритетными являются `T-01`, `T-02`, `T-05`, `T-08`.

Они выбраны потому, что покрывают главную границу доверия продукта: кто может обращаться к заметкам, как сервис обрабатывает недоверенный ввод и можно ли воспроизвести оцениваемую версию.
