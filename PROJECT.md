# PROJECT: Notes Service

## 1. Краткое описание

Notes Service - минимальный backend-сервис для личных заметок. Пользователь хранит небольшие текстовые записи, помечает их тегами, может просмотреть список, открыть отдельную заметку, изменить ее, архивировать или удалить.

Проект сделан для EK1 как минимальная запускаемая техническая основа. Это означает, что реализован работающий HTTP API и базовые проверки, но не реализованы полноценные учетные записи, постоянная база данных, frontend, доставка уведомлений и совместное редактирование.

## 2. Цели продукта

Основная цель: дать пользователю простой способ хранить личные заметки через API.

Практические цели EK1:

- показать границу доверия продукта;
- описать активы, угрозы, требования безопасности и проектные решения;
- подтвердить, что есть запускаемая техническая основа;
- показать воспроизводимые команды запуска и проверки;
- зафиксировать вклад и использование ИИ.

## 3. Пользовательские сценарии

### UC-01 Создать заметку

Пользователь отправляет `POST /notes` с заголовком, содержимым и тегами. Сервис проверяет bearer token, валидирует поля и сохраняет заметку в in-memory хранилище.

Успех: возвращается `201` и созданная заметка с `id`, `createdAt`, `updatedAt`.

Ошибка: без token возвращается `401`, с некорректными полями - `400`.

### UC-02 Посмотреть список заметок

Пользователь отправляет `GET /notes`. Сервис проверяет token и возвращает только заметки текущего владельца.

Успех: возвращается JSON `{ "notes": [...] }`.

Ошибка: без token возвращается `401`.

### UC-03 Открыть заметку

Пользователь отправляет `GET /notes/:id`. Сервис проверяет token и ищет заметку только среди записей текущего владельца.

Успех: возвращается JSON `{ "note": ... }`.

Ошибка: если заметки нет или она не принадлежит владельцу, возвращается `404`.

### UC-04 Изменить заметку

Пользователь отправляет `PATCH /notes/:id` с изменяемыми полями. Сервис проверяет token, принадлежность заметки и валидирует новые значения.

Успех: возвращается обновленная заметка, поле `updatedAt` меняется.

Ошибка: некорректные поля дают `400`, отсутствие доступа - `401` или `404`.

### UC-05 Удалить заметку

Пользователь отправляет `DELETE /notes/:id`. Сервис проверяет token и удаляет заметку текущего владельца.

Успех: возвращается `204`.

Ошибка: чужая или несуществующая заметка дает `404`.

## 4. Активы

| Актив | Почему важен | Пример нарушения |
| --- | --- | --- |
| Содержимое заметок | Может содержать личные планы, учебные материалы, ссылки, черновики | Чтение чужой заметки |
| Метаданные заметок | Теги, время создания и обновления раскрывают контекст пользователя | Перебор id и анализ активности |
| Право изменения/удаления | Потеря целостности разрушает основной сценарий | Изменение или удаление чужой заметки |
| Конфигурационный token | Дает доступ ко всем операциям с заметками в минимальной версии | Утечка `NOTES_API_TOKEN` |
| История Git и tag/commit | Нужны для проверки EK1 и наблюдаемости вклада | Нельзя понять, какая версия оценивается |

## 5. Граница доверия

Граница доверия проходит по входящему HTTP-запросу.

Недоверенные данные:

- URL и параметр `:id`;
- HTTP-метод;
- заголовок `Authorization`;
- `Content-Type`;
- JSON-тело запроса;
- поля `title`, `content`, `tags`, `archived`.

Доверенные данные на EK1:

- переменная окружения `NOTES_API_TOKEN`;
- переменная окружения `PORT`;
- код сервиса;
- in-memory хранилище внутри процесса.

Важное ограничение: сейчас все авторизованные запросы считаются запросами одного владельца `default-user`. Это осознанное упрощение для EK1. Архитектура уже содержит поле `ownerId`, поэтому будущий переход к настоящим пользователям не требует переписывать доменную модель заметки.

## 6. Минимальная архитектура

```text
HTTP client
  |
  | недоверенный HTTP-запрос
  v
src/http.ts
  - разбор URL
  - healthcheck
  - проверка bearer token
  - чтение JSON с лимитом
  - единый формат ответов
  |
  v
src/store.ts
  - валидация полей заметки
  - owner-scoped CRUD
  - in-memory Map<string, Note>
  |
  v
Note domain object
```

## 7. Запуск

Требования:

- Node.js 22+;
- pnpm 10.x.

Установка:

```bash
pnpm install
```

Сборка:

```bash
pnpm build
```

Запуск в Linux/macOS:

```bash
NOTES_API_TOKEN=dev-token pnpm start
```

Запуск в PowerShell:

```powershell
$env:NOTES_API_TOKEN = "dev-token"
pnpm start
```

Порт по умолчанию: `4300`. Его можно изменить через `PORT`.

## 8. Проверка работоспособности

Healthcheck:

```bash
curl http://localhost:4300/health
```

Ожидаемый ответ:

```json
{"status":"ok","service":"notes-service"}
```

Запрос без token:

```bash
curl http://localhost:4300/notes
```

Ожидаемый результат: `401`.

Запрос с token:

```bash
curl -H "Authorization: Bearer dev-token" http://localhost:4300/notes
```

Ожидаемый результат:

```json
{"notes":[]}
```

Создание заметки:

```bash
curl -X POST http://localhost:4300/notes \
  -H "Authorization: Bearer dev-token" \
  -H "Content-Type: application/json" \
  -d "{\"title\":\"EK1\",\"content\":\"План защиты\",\"tags\":[\"security\"]}"
```

## 9. Автоматические проверки

```bash
pnpm test
pnpm typecheck
pnpm build
```

`pnpm test` проверяет основной CRUD, отказ без token, валидацию, JSON-ошибки, security header и изоляцию по `ownerId` на уровне `NotesStore`.

## 10. Что намеренно не реализовано к EK1

- постоянная база данных;
- регистрация пользователей;
- refresh token, JWT, OAuth;
- web frontend;
- rate limiting;
- аудит действий;
- шифрование заметок на уровне приложения;
- поиск по заметкам.

Эти ограничения зафиксированы, потому что EK1 оценивает концепцию безопасности на минимальной технической основе, а не полноту конечного продукта.
