# Defense Guide

Этот файл - короткий сценарий для очной защиты EK1. Его можно открыть прямо в репозитории и идти по разделам.

## 1. Вступление на 30-40 секунд

“Наш продукт - Notes Service, минимальный backend для личных заметок. Пользователь может создать заметку, получить список, открыть, обновить, архивировать или удалить запись. К EK1 мы сделали запускаемый HTTP API и концепцию безопасности: описали активы, границу доверия, угрозы, требования, решения и проверки. Полный frontend, регистрация и база данных пока не входят в объем EK1”.

Что открыть:

- `README.md`;
- `PROJECT.md`, разделы 1-6.

## 2. Что является границей доверия

Короткий ответ:

“Мы считаем недоверенным весь входящий HTTP-запрос: метод, URL, note id, заголовки, JSON-body и все поля заметки. Доверяем только конфигурации процесса и коду сервиса. Поэтому перед работой с заметками запрос проходит token-проверку, JSON читается с лимитом, а поля валидируются”.

Что показать:

- `PROJECT.md`, раздел “Граница доверия”;
- `src/http.ts`, `requireBearerToken` и `readJson`;
- `src/store.ts`, валидаторы.

## 3. Главная цепочка защиты

Говорим цепочку:

```text
T-01 Unauthorized Disclosure
  -> SR-01 Authentication Required + SR-02 Note Ownership Isolation
  -> D-01 Token Gate And Owner-Scoped Store
  -> D-01-V1 / D-01-V4
```

Расшифровка:

- угроза: пользователь получает возможность прочитать чужую заметку;
- требования: все операции с заметками требуют token, а доступ к объекту должен проверяться по владельцу;
- решение: HTTP-слой проверяет bearer token, а `NotesStore` работает не просто по `id`, а по `ownerId + id`;
- проверка: `D-01-V1` подтверждает `401` без token, а `D-01-V4` подтверждает `404` для чужого `ownerId` на уровне `NotesStore`.

Что показать:

- `docs/ek1/traceability.md`, Chain A;
- `docs/ek1/security-decisions.md`, `D-01`;
- `test/run-tests.ts`.

## 4. Почему token, а не полноценная регистрация

Ответ:

“На EK1 нужно показать минимальную запускаемую основу и концепцию безопасности. Полная регистрация добавляет пароли, восстановление доступа, refresh token, хранение пользователей и много новых угроз. Мы выбрали bearer token как минимальный механизм, который уже показывает границу доверия. При этом модель заметки содержит `ownerId`, поэтому переход к настоящим пользователям запланирован без переделки доменной модели”.

Ссылка:

- `docs/ek1/security-decisions.md`, `D-01`;
- `docs/ek1/security-requirements.md`, `SR-09`.

## 5. Почему in-memory storage допустим

Ответ:

“EK1 не требует production-хранилища. Минимальная основа должна запускаться локально и иметь понятную границу. In-memory хранилище достаточно, чтобы показать API, авторизацию, owner isolation, валидацию и тесты. При этом в требованиях и решениях мы заранее описали, что при переходе к БД нужны `owner_id`, ограничения схемы и update/delete с условием по владельцу”.

Ссылка:

- `PROJECT.md`, раздел “Что намеренно не реализовано к EK1”;
- `docs/ek1/security-decisions.md`, `D-04`;
- `docs/ek1/security-requirements.md`, `SR-09`.

## 6. Почему `404`, а не `403` для чужой заметки

Ответ:

“Если вернуть `403`, API подтвердит, что объект с таким id существует, но принадлежит другому пользователю. Мы выбрали `404`, чтобы не раскрывать факт существования чужой заметки. Это закрывает часть угрозы object enumeration”.

Ссылка:

- `docs/ek1/security-requirements.md`, `SR-02`;
- `docs/ek1/threat-model.md`, `T-03`;
- `src/store.ts`, метод `get`.

## 7. Что показать для запуска

Команды:

```bash
pnpm install
pnpm test
pnpm build
```

Запуск:

```powershell
$env:NOTES_API_TOKEN = "dev-token"
pnpm start
```

Проверка:

```bash
curl http://localhost:4300/health
curl -H "Authorization: Bearer dev-token" http://localhost:4300/notes
```

Ожидаемый результат:

- healthcheck возвращает `ok`;
- `/notes` с token возвращает список;
- `/notes` без token возвращает `401`.

## 8. Адресные вопросы и короткие ответы

### Какие активы защищаете?

Содержимое заметок, метаданные заметок, право изменения/удаления и конфигурационный token. Commit/tag важны для сдачи EK1, но не являются security asset самого Notes Service.

### Самая важная угроза?

`T-01 Unauthorized Disclosure`, потому что она напрямую нарушает конфиденциальность: личные заметки становятся доступными для чтения без права. Для изменения и удаления отдельно выделена `T-10 Unauthorized Modification Or Deletion`.

### Почему commit/tag не входят в модель угроз продукта?

Потому что commit hash и tag `ek1` относятся к процессу сдачи, а не к безопасности Notes Service как продукта. Эта информация вынесена в `SUBMISSION.md`, `README.md` и `PROJECT.md`, чтобы не смешивать product security requirements с организационными требованиями EK1.

### Что уже реализовано?

HTTP API, bearer-token gate, in-memory owner-scoped store, валидация, лимит JSON-body, единые JSON-ошибки, `nosniff`, тесты, документация EK1.

### Что не реализовано и почему?

Регистрация, БД, rate limiting, аудит, шифрование и frontend. Это осознанно вынесено после EK1, потому что текущая точка требует минимальную запускаемую основу и концепцию безопасности.

### Что будете делать следующим шагом?

Добавить настоящих пользователей, постоянную БД с `owner_id`, миграции с ограничениями, rate limiting, аудит операций и CI.

1. 30 секунд: что за продукт и какие сценарии.
2. 60 секунд: граница доверия и активы.
3. 90 секунд: приоритетные угрозы, особенно `T-01`.
4. 90 секунд: цепочка `T-01 -> SR-01/SR-02 -> D-01 -> D-01-V1/D-01-V4`.
5. 60 секунд: запуск и проверки.
6. 30 секунд: ограничения EK1 и следующий шаг.

## 10. Что важно не сказать случайно

- Не говорить, что это production-ready сервис.
- Не говорить, что token-авторизация равна полноценной системе пользователей.
- Не говорить, что все будущие проверки уже выполнены.
- Не двигать tag `ek1` после сдачи без согласования с преподавателем.
- Не показывать реальные секреты, если они появятся локально.
